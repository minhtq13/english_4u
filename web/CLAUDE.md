# web - Nuxt 4 SPA + Supabase

Run every npm command under Node 24 (`.nvmrc`); the machine default is Node 20, which Nuxt rejects:

```bash
source ~/.nvm/nvm.sh && nvm use && npm run typecheck && npm run build
```

A change is done when `npm run typecheck`, `npm test` (vitest, `tests/`; it includes the i18n key check) and `npm run build` all pass, and every new UI string is in both locales (`.claude/rules/web-i18n.md`). The tests run plain modules in Node without Nuxt, so a util or composable under test imports what it uses (`./i18n`, `./course`, `vue`) instead of relying on auto-imports. Logged-in flows can be driven in a headless browser with the test accounts `test.admin` / `gv.02` (teacher) / `hs.04` (student) (`hs.04` is in class 6T2; `gv.02` teaches no class until an admin assigns one, e.g. a throw-away class made for the check), whose passwords are in the gitignored `.env.test`; say plainly which flows were not tried in a browser.

## Architecture

- **SPA** (`ssr: false`), Vercel Root Directory `web`, env `SUPABASE_URL` / `SUPABASE_KEY`. There are no server routes; all data goes browser → Supabase.
- **Authority is the database.** RLS policies and triggers decide who reads and writes what; the UI only mirrors them. Every permission change is a migration (`db-migration` skill), never a client-side check alone.
- **Roles**: `student`, `teacher`, `admin` (`profiles.role`). Pages declare `definePageMeta({ roles: [...] })`, enforced by `app/middleware/access.global.ts`; admins pass everywhere. Students join a class once by code (`join_class` RPC); teachers see only classes in `class_teachers`. Lessons belong to a grade; a class sees a lesson (row, content, everything) only once it is assigned to that class by a row in `class_lessons`. Working on it (start, save, submit) needs `private.can_work_lesson`: the lesson is not `closed` nor past `due_at` (a pg_cron job, `close-due-lessons`, closes past-due lessons every minute and submits work in progress), and it is `for_all` or the student is in `class_lesson_students`; reading content also lets in a student who already has an attempt (review). `close_class_lesson()` closes and auto-submits; deleting an assignment is refused once the class has attempts. `app/utils/attemptOutcome.ts` mirrors this for the UI: `accessOf()` / `isClosed()` (closed or past due), and `attemptOutcome(row, viewer, showResults)` for whether a viewer may see an attempt's score, the score (`toScore()`) and its status label; pages read these instead of deciding themselves. Every read and write of `class_lessons` / `class_lesson_students` goes through `app/utils/classLessonStore.ts` (give, take back, settings, chosen students, close, release; what a teacher, the lesson editor and a student each read, incl. `lessonForStudent()` for access), never a `from("class_lessons")` in a page; `useClassLessons(classId)` keeps one class's state on top of it and `useClassWorkspace()` adds what each change moves (numbers, who owes work, the busy key and the notice) for the class page; tests run the store against `tests/helpers/memoryClient.ts`; "Thu hồi" shows only while `class_lesson_stats.started` is 0 (the delete trigger refuses once any attempt exists), and `takeBackLesson()` asks the deleted row back so an RLS no-op reports an error; the class page shows each action's outcome inside that lesson (`notice`), not at the page top. A given lesson folds to one summary line (`openLessons`, "expand all" beside the filters); unfolded, its "Tình trạng nộp bài" button opens `LessonProgressDialog` (every student of the class and where they stand on that lesson: not started, working, waiting for a grade, graded, or not given the lesson, from `lessonStates()` in `app/utils/lessonStatus.ts`; `ClassLessonProgress` reads what it needs by class and lesson), the same popup the lesson page (`/lessons/<id>`, teacher preview) opens for the classes that have the lesson; a lesson that cannot be taken back keeps a disabled "Thu hồi" button with an `InfoTip` saying why; the lesson's "Sửa bài" button sits with its state badges, not in the title; the "Chưa nộp: N" button in its block opens `MissingWorkDialog` (who has not submitted, reminder text to copy); the class's students are `ClassStudents` (search, who to show, order via `filterStudents()` in `app/utils/studentFilter.ts`, pages of 10, all in the browser since a class is small). A teacher's actions on one attempt (read it with feedback and results, release, redo through the `allow_redo()` RPC in one transaction, write / edit / delete feedback, the grading queue helpers) are `app/utils/attemptReview.ts`; "Chấm lần lượt" is `useGradingQueue()` on top of it. On the class page (`/teacher/classes/<id>`) a lesson that is not given yet opens `ClassLessonSetup` (what it contains, which classes of the grade already have it, deadline, whole class or chosen students, results at submit, shuffle); nothing is saved until its "Giao cho lớp" button inserts the `class_lessons` row with those settings (`GiveSettings` in `app/utils/classLesson.ts`) and the `class_lesson_students` rows.
- **Student extras** (migrations 44-51). `study_days` (streak, `utils/streak.ts`, `useStudyDays()`/`StreakCard`) is written by a trigger on the student's own saves only. `notifications` are written by triggers (lesson given, graded, feedback, class announcement) and the hourly `notify-due-soon` job, never by the client; they hold a `kind` + `params`, worded by `utils/notifications.ts` and the `notifications.kind.*` keys (`useNotifications()`, `NotificationBell`, `/notifications`; a Realtime channel on `notifications` (migration 50) with a one-minute poll as fallback, one channel per bell since the sidebar and the phone header each have one); `class_announcements` are posted by the class's teachers (`ClassAnnouncements`). A lesson can have a time limit (`class_lessons.time_limit_min`): the clock is the database's (`attempts.timer_started_at`, `private.can_work_lesson()` refuses writes after it, the `submit-timed-out` cron job submits), the page only shows `LessonTimer`. `card_reviews` (Leitner boxes, `utils/srs.ts`, `/review`) schedule flashcards; "practise what I got wrong" (`/practice/<lesson>`, `utils/practice.ts`) rebuilds the lesson from the questions the student got wrong and grades in the browser, saving nothing.
- **Badges** (migration 55). `badges` (key, target) and `user_badges` are written only by the `my_badges()` RPC, which counts the caller's own work (on-time hand-ins, perfect scores, streaks, course done, 50 reviewed cards, 100% in under 10 minutes), records what was just reached and returns every badge with progress; results not yet released to the student never count. `useBadges()` calls it (home page and `BadgesCard` on `/account`); `BadgePopup` (default layout) shows the badges whose `is_new` is true. A new badge is a row in `badges`, a case in `my_badges()`, an entry in `BADGE_ICONS` and `badges.<key>.*` i18n keys.
- **Class marks** (migrations 58-59). What happens in class, per class and term (`term` 1/2, default `termOf()`: August-December is 1): `class_sessions` + `attendance` (present / late / excused / absent per session, one session per class and day), `participation_points` (one row per +1 for speaking up, undone by deleting it), `score_columns` (`kind` `oral` = kiểm tra bài cũ, `homework`) + `score_entries` (0-10). The class's teachers and admins write (RLS through `private.teaches_class`, with `private.class_of_session()` / `class_of_column()` for the child tables); a student reads only their own rows; the trigger `private.check_score_student()` refuses a student who is not in that class. `app/utils/classScoreStore.ts` is the only place that reads or writes these tables (tests on `memoryClient`, which also does `upsert`); `app/utils/classScores.ts` computes (attendance mark: 10, minus 1 per unexcused absence and 0.5 per late, never below 0; means of each kind). Teacher page `/teacher/scores/<class>` (linked from the class page, tabs in `?tab=`, steps in `components/class-scores/`: Attendance, Participation, ScoreColumns, Summary with the Excel file); students see `MyClassScores` on `/progress`. These screens are built from the app's shared pieces, not their own look: `.opts` buttons (a chosen status adds its colour, in fixed grid columns so rows line up), `.scorebar savebar` for the sticky save bar, `.list-row`, `.badge`, `.stats` / `.stat`, `EmptyState`, `StatBar`, the gradebook's table, and `ClassScoresMark` (a 0-10 mark as a pill, band from `scoreBand()`: 8 and over, 5 and over, below). Every field is a real `type` (`text` / `date`) so the global input style applies; `input[type=date]` is in that rule in `main.css`.
- **Error log** (migration 56). `plugins/error-log.client.ts` sends Vue errors, uncaught errors and unhandled rejections of a signed-in person to `log_client_error()` (filtered and throttled by `utils/errorReport.ts`). `client_errors` is a ring buffer of 1000 slots (a new error overwrites the oldest slot, so nothing is ever deleted: the MCP refuses functions that delete), readable by admins only at `/admin/errors`. The admin dashboard's charts (`utils/adminCharts.ts`: hand-ins per day, top classes, score bands) are counted in the browser from the last 30 days of `attempts`; embedding `classes` from `profiles` needs the hint `classes!profiles_class_id_fkey`.
- **Teacher and admin extras**: `TeacherToday` (`utils/todayTasks.ts`) on `/teacher`; `/teacher/gradebook/<class>` (`utils/gradebook.ts`) and `/teacher/analysis/<class>` (RPC `question_analysis`, `utils/questionAnalysis.ts`), both with Excel (.xlsx) export through `downloadXlsx()` in `utils/spreadsheet.ts` (title, a note saying what the numbers are, bold header; exceljs is imported only when a file is saved; every export in the app uses it, never write a CSV by hand); grading shortcuts in `utils/gradingKeys.ts`; "Nhân bản" opens the editor with `?copy=<lesson>`. Paper exam sets: `/teacher/exams` lists the saved sets (`exam_sets`, migration 52: owner or admin by RLS, questions stored as a jsonb snapshot with answers and passages; `utils/examStore.ts` is the only place that reads or writes the table, update and delete ask the row back), `/teacher/exams/new` and `/teacher/exams/<id>` are one page (`[id].vue`) that saves with "Lưu bộ đề", shows whether the form differs from the stored row (`snapshotOf()`) and asks before leaving unsaved edits of a saved set; the form is also a working copy in `localStorage` (`utils/examDraft.ts`, with `examId`) so an unsaved new exam survives a reload and the print page can lay out unsaved edits. Building one: questions picked from `useQuestionBank()` or drawn by a matrix from `useExamPool()` (`section_items` with their section, for the reading passage), `utils/examGenerator.ts` (parts, `buildVariant(parts, code, mode)`: every shuffle is seeded by the exam code, a passage keeps its questions together, `answerMatrix()`), `utils/exportDocx.ts` (Word paper and the copy with solutions, `docx` imported only when a file is made, a `lazy-` chunk left out of the precache like exceljs) and `utils/exportExcel.ts` (answer matrix + detail sheets through `xlsxBytes()`); `ExamPreview` shows the same variant on the page. The order of the list of questions is the printed order: parts come in the order of their first question (`buildParts()`), so reordering parts is just reordering the list (`movePartTo()`, `moveBlockTo()`, `addQuestion()` places a new part by the usual order among the parts already there, `canonicalOrder()` is for a fresh matrix draw); dragging is the `v-sortable` directive (`utils/sortable.ts`, SortableJS in pointer mode, grips only, puts the DOM back and lets Vue render the new order) with arrow buttons as the keyboard way. **Sharing** (migration 54): the owner or an admin shares a set with other teachers and admins only (`exam_set_shares`, `can_edit` false = view only; `private.is_staff()` refuses anyone else in the insert policy), through `ExamShareDialog`; RLS lets a person it is shared with read it and, with `can_edit`, update it, never delete it or change `owner_id` (guard trigger) or the shares; they can drop their own share. `examAccess()` (`manage` / `edit` / `view`) mirrors this in the UI (`/teacher/exams` list and the builder, which is read-only with "Tạo bản sao để sửa" for `view`). Teachers cannot read each other's `profiles`, so names of owners and of people to share with come from the `staff_directory()` RPC (`searchStaff()` / `staffByIds()`), and the list embeds the owner as `profiles!exam_sets_owner_id_fkey(...)` because the shares table gives PostgREST a second path from exam sets to profiles. Which parts are shuffled: `exam_sets.fixed_parts` (migration 60) lists the parts that print the same on every code (`buildVariant(parts, code, mode, fixed)`: a fixed part ignores the code, whatever the mode; `cleanFixed()` keeps known keys; empty = shuffle every part, the default), chosen in step 4 before the shuffle mode. On the paper (preview, PDF and Word) a rewriting question (`order`) and a free-answer `typed` question get one ruled line to write on, while a `typed` fill-in prints its blank longer (`WORD_BLANK` in Word, `.blank` in the preview) and no extra line (`needsAnswerLine()`, `hasBlank()` in `utils/examGenerator.ts`); the line in the preview is a `<div>`, because `.question :deep(p)` is inline and an empty `<p>` has no height. Shuffling a code again: `exam_sets.shuffle_rounds` (migration 61, `{code: n}`) adds a counter to the seed (`buildVariant(..., fixed, round)`; round 0 is the first shuffle, so every older set prints as before; `cleanRounds()` keeps whole numbers 1..999 for the codes in use); step 5 has "Shuffle code N again", "Back to the last shuffle" and "Shuffle all", and the counters are saved with the set and used by the print page. The answer sheet is a switch beside the preview in step 5 (`sheet_at` stays `top` / `bottom` / `none`; off = `none`, so it travels with the saved set and the print page). The cards of the builder and each part of the base exam fold (`ExamCollapse`, `ExamFoldToggle`, `useFolds()`; kept in this browser, toggles are `div role=button` because the builder sits in a `<fieldset disabled>` for view-only people). Each part's instruction line is `exam_sets.part_hints` (migration 53), written by the author or else the default `exam.part.<key>.hint` (`partHintOf()`). A question can be read in full before it is chosen (`QuestionPreviewDialog`, from `useExamPool().ofIds()`); the PDF is `/teacher/exams/print` (the browser's print dialog → "Save as PDF", reading the draft from `utils/examDraft.ts`), not a PDF library. A list paged in the database needs a unique sort key (`.order("lesson_id").order("id")`), or PostgreSQL may return one row on two pages. Admins: `/admin/logins` (`login_log`), `/admin/audit` (`audit_log`, written by triggers; a lock or delete made through the manage-accounts edge function has no actor unless the function version that calls `auditActor()` is deployed), and `promote_class()` (a whole class to another, one audit row) and `graduate_class()` (migration 57: grade 9 leaves its class, attempts stay, one audit row), both run from `PromoteDialog` ("Lên lớp" on `/admin/classes`; `planPromotion()` in `utils/promotion.ts` pairs 6T1 → 7T1 and runs from the highest grade down, so a class just moved up is not moved twice).
- **Big pages are split into step components**, each owning its own scoped styles (a parent's scoped CSS does not reach a child's inner elements): the exam builder's steps `components/exam/Step{Info,Codes,Export}.vue`, the lesson editor's `lesson-editor/{Steps,SetupGrade,Info}.vue` (+ `ImportDialog` for pasting questions from text), `AttemptFeedback` (comment form, earlier comments, grading shortcuts) on the attempt page and `ClassLessonBody` (an unfolded given lesson) on the class page, which takes the page's `useClassWorkspace()` result as a prop.
- **Primary colour** (`useAccent()`, `utils/accents.ts`, `AccentPicker` on `/account`): `data-accent` on `<html>` selects a preset set of `--accent` / `--accent-soft` / `--on-accent` in `main.css` (light, and dark under both selectors; `tests/accents.test.ts` checks contrast). A colour of the person's own is `data-accent="custom"`: `customAccent()` works out a light and a dark set that stay readable (contrast 4.5), set inline as `--c-*` / `--cd-*`; the cookies `accent`, `accentHex`, `accentVars` let the inline script in `nuxt.config.ts` apply it before the app starts.
- **Hidden answers**: students never read `section_items`. Lesson questions come from the `lesson_items()` RPC, which strips the answer key until results are released. Students save only their choices in `attempts.answers`; `submit_attempt()` grades on the server, exactly once; graded answers live in `attempt_results`. `class_lessons.show_results` releases results at submit, otherwise on teacher grading. Teachers and admins open lessons in preview (key shown, nothing saved). While a student works on a lesson (not preview, not submitted or closed), `useAntiCheat()` on the lesson page blocks selecting, copying, pasting into answers, the context menu, dragging, print / save / view-source shortcuts and machine translation (`exam-mode` class on `<html>`; printing shows a notice instead), and `ExamWatermark` lays the student's name, login and time faintly over the page; answer inputs carry `spellcheck` / `autocorrect` / Grammarly off. It only discourages (a phone camera still works); nothing here is enforced by the database.
- **Accounts**: students (and teachers given one) log in with a username + password issued at `/teacher/students` and `/admin/teachers` (`AccountManager`). A username is the auth email `<username>@users.english4u.internal` (`loginEmail()` in `app/utils/accounts.ts`); Google login remains for admins/teachers but its button on the login page is behind the flag `runtimeConfig.public.enableGoogleLogin` (default `false`; set `NUXT_PUBLIC_ENABLE_GOOGLE_LOGIN=true` to show it; the Google provider itself is switched in Supabase). Creating, renaming, resetting passwords, locking (ban + `profiles.active`) and deleting accounts need the service role, so they go through the edge function `supabase/functions/manage-accounts` (deployed with the Supabase MCP `deploy_edge_function`, `verify_jwt: false` because it authenticates the caller itself). The function is the authority there: admins manage anyone but themselves; teachers only students of their classes. Keep its domain constant in sync with `LOGIN_DOMAIN`. `profiles.username` changes only through the function (a guard refuses anyone but `service_role`, migration 43), because the login email must change with it. **Sessions** are enforced in the database (migration 40): one per account (a new sign-in deletes the account's other `auth.sessions` rows, so the other device is signed out), ended after 10 minutes without activity (`useSessionGuard()` in the default layout reports activity through `touch_session()` at most once a minute; the `end-idle-sessions` pg_cron job deletes sessions not seen for 10 minutes; `IDLE_MS` must match it), and ended at once when an account is locked (trigger on `profiles.active`). Every table carries a restrictive `session alive` policy (`private.session_alive()`), so any request from a deleted session's JWT fails with SQLSTATE `PT401` (HTTP 401), which `plugins/session-ended.client.ts` turns into an immediate sign-out with the reason; give a new table the same policy. Every sign-in and how it ended is in `login_log`; `SessionEndedDialog` (default layout) says why the session ended and leads to the login page. The security definer RPCs start with `perform private.session_alive()` (migration 42); a new one does the same. Edge functions are Deno code (`npm:` imports): the Nuxt typecheck skips them, and editors check them through the Deno extension (`.vscode/settings.json` → `deno.enablePaths`).
- **Content model**: `courses → phases → lessons → lesson_sections → section_items`, mapped to UI types by `toLesson()` in `app/utils/course.ts`. Question ids are `score_key + item number` (e.g. `M3`); items carry their original number `n`, and every qid is built with `qidOf()` - never from the display index, because `shuffleLesson()` (per-student order when `class_lessons.shuffle`) reorders items and options.
- **Section types**: `explain`, `cards`, `writing` (unscored) and `mcq`, `typed`, `order`, `match`, `error` (scored, graded in `private.grade_attempt()` and mirrored by `gradeLocal()`). `match` pairs `prompt`/`back`; `lesson_items()` hides `back` until release and returns every right side of the section, shuffled, in `options`. `error` stores a sentence's chunks in `options` with the wrong one in `correct_option`; `shuffleLesson()` never reorders its chunks. `mcq`/`typed` may carry a shared reading passage in `lesson_sections.body`. `[x]` in an option or chunk is shown underlined by `markUnderline()` and compared raw when grading. Exam-format starters for the editor are `SECTION_PRESETS` in `app/utils/lessonDraft.ts`. Each scored type is one entry in `SECTION_KINDS` (`app/utils/sectionKinds.ts`): stored row → question, browser grading, save payload, row → draft, draft checks, one-line question and answer. The editor preview (`draftToLesson`) is the save payload served the way `lesson_items()` serves it, read by `toLesson()`, so it cannot drift from a saved lesson. A new scored type is a `SECTION_KINDS` entry plus a `toSection` case, its section component in `LessonQuestions`, `LessonWorksheet`, and the database (`validate_section_item`, `lesson_items`, `grade_attempt`); `tests/sectionKinds.test.ts` pins browser grading to the database's rules.
- **Lesson editor** (`/teacher/lessons/new`, `/teacher/lessons/<id>`): teachers build lessons in a grade they teach from a structure template, saved whole by the `save_lesson()` RPC with an id from `next_lesson_id()`. The editor's last card (`LessonEditorGiving` + `useLessonGiving()`) gives the lesson to classes of the grade when it is saved: per class the same `GiveSettingsForm` as the class page's give panel (deadline, who may work, results at submit, shuffle; the last two carry an `InfoTip`). New classes are given the lesson through `giveLesson()`; a class that already has it keeps it and gets only the settings that changed (`updateGivenLesson()`); one that is closed or past due is left to the class page, and taking back is only there. Saving again after a failure retries just what failed (`savedId`). Only the author (`lessons.created_by`) or an admin edits a lesson. A new lesson goes through two stages on one page: setup (grade, term, then the structure step, `lesson-editor/Structure.vue`) and content; an existing lesson opens at its content. The structure step starts from the standard layout, the exam layout (`EXAM_STRUCTURE`), blank, a structure the teacher saved (`lesson_structures`: `structureOf()` stores only section type, title, time, hint, `short`, question count and the exam-preset key, never questions; `sectionsFromStructure()` rebuilds it) or another lesson. Starter questions of a preset (`SECTION_PRESETS`) are built inside `make()`, because `tr()` needs the running app. Draft logic lives in `app/utils/lessonDraft.ts`. Deleting a lesson (lesson list `/courses/<id>` and the editor) goes through `useLessonDelete()`: only the author or an admin (RLS), sections, questions and class assignments cascade, and the database refuses once any student has an attempt (`attempts.lesson_id` is `ON DELETE RESTRICT`), which `lessonDeleteError()` turns into a Vietnamese message; the delete asks for the deleted row back because RLS silently deletes nothing otherwise. Lessons with attempts are read-only. Teachers never type HTML: formatted fields use `RichEditor` (Tiptap; custom `Keyword` = `em.g` and `Callout` = `div.box`/`div.warn` in `app/utils/editorExtensions.ts`), and fields compared when grading (options, answers, order chunks) stay plain inputs. Lesson HTML is rendered through DOMPurify (`safeHtml`); grading compares raw option/answer text, so sanitise only for display.

## Conventions

- `app/types/database.types.ts` is hand-maintained (with `Tables` / `Views` / `Enums` helpers). Add every new table, view, column and RPC there in the same change.
- Hold fetched DB rows in `shallowRef`; a deep `ref` over the recursive `Json` type triggers TS2589.
- The signed-in user id is `useSupabaseUser().value?.sub` (the value holds JWT claims, not a User).
- PostgREST returns embedded rows unordered: sort by `position` on the client.
- Shared UI pieces: `useToast()` + `ToastHost` for the outcome of an action (inline `fb` stays for text tied to one field), `EmptyState` for a list with nothing in it, `StudentTabs` (phone bottom bar; hidden on lesson pages), `SubmitDialog` / `LessonSectionNav` / `LessonResult` (lesson page, from `utils/lessonProgress.ts`), `SpeakButton` (`utils/speech.ts`, browser voices), `BackLink` for back navigation, `useServerList(fetch, { pageSize, filters })` + `Pager` for a list paged in the database (debounced filters, back to page 1, a stale response dropped, `error`; search text through `filterTerm()` / `personSearch()` / `likeTerm()` in `app/utils/search.ts`), `usePaged()` for paging a list already loaded whole, `AttemptHistory` for one learner's attempts, `ScrollTop` (in the default layout: a back-to-top button on long pages that rises above a sticky `.savebar`, so give a new sticky bottom bar that class), `Icon` for every icon (Lucide line icons in `app/components/Icon.vue`; add a path there, never an emoji), `Skeleton` while a page or panel loads (not a "loading" line), `stack-table` on a table that must read on phones (each `td` gets `:data-label` = its column; `no-label` for an actions cell), `ThemeSwitch` + `useTheme()` for light / dark / device (the `theme` cookie sets `data-theme` on `<html>`; dark tokens in `main.css` exist twice, under the media query and under `[data-theme="dark"]`, so change both), `useDialog(root, close)` for every popup (Escape, focus moved in, kept inside and given back, page scroll locked; the `role="dialog"` element gets `ref` + `tabindex="-1"`), `InfoTip` for an "i" that explains a label (hover, focus or tap; pointer events, kept inside its card), `GiveSettingsForm` for how a lesson is given to one class (`GiveForm`, `settingsOf()` / `formOf()` / `giveProblem()` in `app/utils/classLesson.ts`), `useQuestionBank()` for the `question_bank` view (the `/teacher/bank` page and the editor's dialog), `useLessonHandoff()` + `sectionsFromQuestions()` to open a lesson built on another page (review sheet, bank picks) in the editor (`/teacher/lessons/new?from=<from>`, grade carried over), `LessonFilters` + `useLessonFilter()` for lesson lists (search without accents via `fold()`, kind from the label via `lessonKind()`, term, author, a page-specific status), `StatBar` for meters, `percentOf(part, whole)` for percentages, `LessonQuestions` for rendering a scored section, `LessonAssign` + `useAssignments()` for giving a lesson to classes.
- Two-click confirmation for destructive buttons (delete, submit, redo), with `useTwoClick()` (`arm(key)` is true on the confirming click).
- A person is named by `personName()` (`app/utils/accounts.ts`: full name, else username, else real email), never by an inline `full_name || email`: a student's auth email is a made-up address.
- **i18n** (`@nuxtjs/i18n`, `no_prefix`, default `vi`, choice kept in the `lang` cookie, switch = `LangSwitch` in the sidebar, login and account pages). Every UI string is a key in `i18n/locales/vi.json` + `en.json` (same keys in both): `$t()` in templates, `const { t } = useI18n()` in `<script setup>`, `tr()` from `app/utils/i18n.ts` in plain utils. Label maps that must follow the language are built with `labels(prefix, keys)` (getters). Seeded course/phase names go through `localName()`; lesson content stays as authored. Database and edge-function errors are raised in Vietnamese; show them through `errorText()` (`app/utils/serverErrors.ts`), and add an English pattern there when you add a new `raise exception`. Messages may hold `<b>` (rendered with `v-html`); `@` and `|` are special in vue-i18n (write `{'@'}`, `{'|'}`), and `|` separates plural forms used as `$t(key, n)`.
- Pin new npm dependencies to an exact version published at least two weeks earlier.

Data-access rules for `app/**` live in `.claude/rules/web-data-access.md`; they load automatically when you edit those files.
