# web — Nuxt 4 SPA + Supabase

Run every npm command under Node 24 (`.nvmrc`); the machine default is Node 20, which Nuxt rejects:

```bash
source ~/.nvm/nvm.sh && nvm use && npm run typecheck && npm run build
```

A change is done when `npm run typecheck`, `npm test` (vitest, `tests/`; it includes the i18n key check) and `npm run build` all pass, and every new UI string is in both locales (`.claude/rules/web-i18n.md`). The tests run plain modules in Node without Nuxt, so a util or composable under test imports what it uses (`./i18n`, `./course`, `vue`) instead of relying on auto-imports. Logged-in flows can be driven in a headless browser with the test accounts `test.admin` / `gv.02` (teacher) / `hs.04` (student) (`hs.04` is in class 6T2; `gv.02` teaches no class until an admin assigns one, e.g. a throw-away class made for the check), whose passwords are in the gitignored `.env.test`; say plainly which flows were not tried in a browser.

## Architecture

- **SPA** (`ssr: false`), Vercel Root Directory `web`, env `SUPABASE_URL` / `SUPABASE_KEY`. There are no server routes; all data goes browser → Supabase.
- **Authority is the database.** RLS policies and triggers decide who reads and writes what; the UI only mirrors them. Every permission change is a migration (`db-migration` skill), never a client-side check alone.
- **Roles**: `student`, `teacher`, `admin` (`profiles.role`). Pages declare `definePageMeta({ roles: [...] })`, enforced by `app/middleware/access.global.ts`; admins pass everywhere. Students join a class once by code (`join_class` RPC); teachers see only classes in `class_teachers`. Lessons belong to a grade; a class sees a lesson (row, content, everything) only once it is assigned to that class by a row in `class_lessons`. Working on it (start, save, submit) needs `private.can_work_lesson`: the lesson is not `closed` nor past `due_at` (a pg_cron job, `close-due-lessons`, closes past-due lessons every minute and submits work in progress), and it is `for_all` or the student is in `class_lesson_students`; reading content also lets in a student who already has an attempt (review). `close_class_lesson()` closes and auto-submits; deleting an assignment is refused once the class has attempts. `app/utils/attemptOutcome.ts` mirrors this for the UI: `accessOf()` / `isClosed()` (closed or past due), and `attemptOutcome(row, viewer, showResults)` for whether a viewer may see an attempt's score, the score (`toScore()`) and its status label; pages read these instead of deciding themselves. Every write to a class's lessons goes through `useClassLessons(classId)` (give, take back, close/reopen, settings, chosen students, release) or its `giveLesson()` / `takeBackLesson()`; "Thu hồi" shows only while `class_lesson_stats.started` is 0 (the delete trigger refuses once any attempt exists), and `takeBackLesson()` asks the deleted row back so an RLS no-op reports an error; the class page shows each action's outcome inside that lesson (`notice`), not at the page top. A given lesson folds to one summary line (`openLessons`, "expand all" beside the filters); unfolded, its "Tình trạng nộp bài" button opens `LessonProgressDialog` (every student of the class and where they stand on that lesson: not started, working, waiting for a grade, graded, or not given the lesson, from `lessonStates()` in `app/utils/lessonStatus.ts`; `ClassLessonProgress` reads what it needs by class and lesson), the same popup the lesson page (`/lessons/<id>`, teacher preview) opens for the classes that have the lesson; a lesson that cannot be taken back keeps a disabled "Thu hồi" button with an `InfoTip` saying why; the lesson's "Sửa bài" button sits with its state badges, not in the title; the "Chưa nộp: N" button in its block opens `MissingWorkDialog` (who has not submitted, reminder text to copy); the class's students are `ClassStudents` (search, who to show, order via `filterStudents()` in `app/utils/studentFilter.ts`, pages of 10, all in the browser since a class is small). "Chấm lần lượt" is `useGradingQueue()`; "Cho làm lại" is the `allow_redo()` RPC (one transaction). On the class page (`/teacher/classes/<id>`) a lesson that is not given yet opens `ClassLessonSetup` (what it contains, which classes of the grade already have it, deadline, whole class or chosen students, results at submit, shuffle); nothing is saved until its "Giao cho lớp" button inserts the `class_lessons` row with those settings (`GiveSettings` in `app/utils/classLesson.ts`) and the `class_lesson_students` rows.
- **Hidden answers**: students never read `section_items`. Lesson questions come from the `lesson_items()` RPC, which strips the answer key until results are released. Students save only their choices in `attempts.answers`; `submit_attempt()` grades on the server, exactly once; graded answers live in `attempt_results`. `class_lessons.show_results` releases results at submit, otherwise on teacher grading. Teachers and admins open lessons in preview (key shown, nothing saved). While a student works on a lesson (not preview, not submitted or closed), `useAntiCheat()` on the lesson page blocks selecting, copying, pasting into answers, the context menu, dragging, print / save / view-source shortcuts and machine translation (`exam-mode` class on `<html>`; printing shows a notice instead), and `ExamWatermark` lays the student's name, login and time faintly over the page; answer inputs carry `spellcheck` / `autocorrect` / Grammarly off. It only discourages (a phone camera still works); nothing here is enforced by the database.
- **Accounts**: students (and teachers given one) log in with a username + password issued at `/teacher/students` and `/admin/teachers` (`AccountManager`). A username is the auth email `<username>@users.english4u.internal` (`loginEmail()` in `app/utils/accounts.ts`); Google login remains for admins/teachers but its button on the login page is behind the flag `runtimeConfig.public.enableGoogleLogin` (default `false`; set `NUXT_PUBLIC_ENABLE_GOOGLE_LOGIN=true` to show it; the Google provider itself is switched in Supabase). Creating, renaming, resetting passwords, locking (ban + `profiles.active`) and deleting accounts need the service role, so they go through the edge function `supabase/functions/manage-accounts` (deployed with the Supabase MCP `deploy_edge_function`, `verify_jwt: false` because it authenticates the caller itself). The function is the authority there: admins manage anyone but themselves; teachers only students of their classes. Keep its domain constant in sync with `LOGIN_DOMAIN`. `profiles.username` changes only through the function (a guard refuses anyone but `service_role`, migration 43), because the login email must change with it. **Sessions** are enforced in the database (migration 40): one per account (a new sign-in deletes the account's other `auth.sessions` rows, so the other device is signed out), ended after 10 minutes without activity (`useSessionGuard()` in the default layout reports activity through `touch_session()` at most once a minute; the `end-idle-sessions` pg_cron job deletes sessions not seen for 10 minutes; `IDLE_MS` must match it), and ended at once when an account is locked (trigger on `profiles.active`). Every table carries a restrictive `session alive` policy (`private.session_alive()`), so any request from a deleted session's JWT fails with SQLSTATE `PT401` (HTTP 401), which `plugins/session-ended.client.ts` turns into an immediate sign-out with the reason; give a new table the same policy. Every sign-in and how it ended is in `login_log`; `SessionEndedDialog` (default layout) says why the session ended and leads to the login page. The security definer RPCs start with `perform private.session_alive()` (migration 42); a new one does the same. Edge functions are Deno code (`npm:` imports): the Nuxt typecheck skips them, and editors check them through the Deno extension (`.vscode/settings.json` → `deno.enablePaths`).
- **Content model**: `courses → phases → lessons → lesson_sections → section_items`, mapped to UI types by `toLesson()` in `app/utils/course.ts`. Question ids are `score_key + item number` (e.g. `M3`); items carry their original number `n`, and every qid is built with `qidOf()` — never from the display index, because `shuffleLesson()` (per-student order when `class_lessons.shuffle`) reorders items and options.
- **Section types**: `explain`, `cards`, `writing` (unscored) and `mcq`, `typed`, `order`, `match`, `error` (scored, graded in `private.grade_attempt()` and mirrored by `gradeLocal()`). `match` pairs `prompt`/`back`; `lesson_items()` hides `back` until release and returns every right side of the section, shuffled, in `options`. `error` stores a sentence's chunks in `options` with the wrong one in `correct_option`; `shuffleLesson()` never reorders its chunks. `mcq`/`typed` may carry a shared reading passage in `lesson_sections.body`. `[x]` in an option or chunk is shown underlined by `markUnderline()` and compared raw when grading. Exam-format starters for the editor are `SECTION_PRESETS` in `app/utils/lessonDraft.ts`. Each scored type is one entry in `SECTION_KINDS` (`app/utils/sectionKinds.ts`): stored row → question, browser grading, save payload, row → draft, draft checks, one-line question and answer. The editor preview (`draftToLesson`) is the save payload served the way `lesson_items()` serves it, read by `toLesson()`, so it cannot drift from a saved lesson. A new scored type is a `SECTION_KINDS` entry plus a `toSection` case, its section component in `LessonQuestions`, `LessonWorksheet`, and the database (`validate_section_item`, `lesson_items`, `grade_attempt`); `tests/sectionKinds.test.ts` pins browser grading to the database's rules.
- **Lesson editor** (`/teacher/lessons/new`, `/teacher/lessons/<id>`): teachers build lessons in a grade they teach from a structure template, saved whole by the `save_lesson()` RPC with an id from `next_lesson_id()`. The editor's last card (`LessonEditorGiving` + `useLessonGiving()`) gives the lesson to classes of the grade when it is saved: per class the same `GiveSettingsForm` as the class page's give panel (deadline, who may work, results at submit, shuffle; the last two carry an `InfoTip`). New classes are given the lesson through `giveLesson()`; a class that already has it keeps it and gets only the settings that changed (`updateGivenLesson()`); one that is closed or past due is left to the class page, and taking back is only there. Saving again after a failure retries just what failed (`savedId`). Only the author (`lessons.created_by`) or an admin edits a lesson. A new lesson goes through two stages on one page: setup (grade, term, then the structure step, `lesson-editor/Structure.vue`) and content; an existing lesson opens at its content. The structure step starts from the standard layout, the exam layout (`EXAM_STRUCTURE`), blank, a structure the teacher saved (`lesson_structures`: `structureOf()` stores only section type, title, time, hint, `short`, question count and the exam-preset key, never questions; `sectionsFromStructure()` rebuilds it) or another lesson. Starter questions of a preset (`SECTION_PRESETS`) are built inside `make()`, because `tr()` needs the running app. Draft logic lives in `app/utils/lessonDraft.ts`. Deleting a lesson (lesson list `/courses/<id>` and the editor) goes through `useLessonDelete()`: only the author or an admin (RLS), sections, questions and class assignments cascade, and the database refuses once any student has an attempt (`attempts.lesson_id` is `ON DELETE RESTRICT`), which `lessonDeleteError()` turns into a Vietnamese message; the delete asks for the deleted row back because RLS silently deletes nothing otherwise. Lessons with attempts are read-only. Teachers never type HTML: formatted fields use `RichEditor` (Tiptap; custom `Keyword` = `em.g` and `Callout` = `div.box`/`div.warn` in `app/utils/editorExtensions.ts`), and fields compared when grading (options, answers, order chunks) stay plain inputs. Lesson HTML is rendered through DOMPurify (`safeHtml`); grading compares raw option/answer text, so sanitise only for display.

## Conventions

- `app/types/database.types.ts` is hand-maintained (with `Tables` / `Views` / `Enums` helpers). Add every new table, view, column and RPC there in the same change.
- Hold fetched DB rows in `shallowRef`; a deep `ref` over the recursive `Json` type triggers TS2589.
- The signed-in user id is `useSupabaseUser().value?.sub` (the value holds JWT claims, not a User).
- PostgREST returns embedded rows unordered: sort by `position` on the client.
- Shared UI pieces: `BackLink` for back navigation, `useServerList(fetch, { pageSize, filters })` + `Pager` for a list paged in the database (debounced filters, back to page 1, a stale response dropped, `error`; search text through `filterTerm()` / `personSearch()` / `likeTerm()` in `app/utils/search.ts`), `usePaged()` for paging a list already loaded whole, `AttemptHistory` for one learner's attempts, `ScrollTop` (in the default layout: a back-to-top button on long pages that rises above a sticky `.savebar`, so give a new sticky bottom bar that class), `Icon` for every icon (Lucide line icons in `app/components/Icon.vue`; add a path there, never an emoji), `Skeleton` while a page or panel loads (not a "loading" line), `stack-table` on a table that must read on phones (each `td` gets `:data-label` = its column; `no-label` for an actions cell), `ThemeSwitch` + `useTheme()` for light / dark / device (the `theme` cookie sets `data-theme` on `<html>`; dark tokens in `main.css` exist twice, under the media query and under `[data-theme="dark"]`, so change both), `useDialog(root, close)` for every popup (Escape, focus moved in, kept inside and given back, page scroll locked; the `role="dialog"` element gets `ref` + `tabindex="-1"`), `InfoTip` for an "i" that explains a label (hover, focus or tap; pointer events, kept inside its card), `GiveSettingsForm` for how a lesson is given to one class (`GiveForm`, `settingsOf()` / `formOf()` / `giveProblem()` in `app/utils/classLesson.ts`), `useQuestionBank()` for the `question_bank` view (the `/teacher/bank` page and the editor's dialog), `useLessonHandoff()` + `sectionsFromQuestions()` to open a lesson built on another page (review sheet, bank picks) in the editor (`/teacher/lessons/new?from=<from>`, grade carried over), `LessonFilters` + `useLessonFilter()` for lesson lists (search without accents via `fold()`, kind from the label via `lessonKind()`, term, author, a page-specific status), `StatBar` for meters, `percentOf(part, whole)` for percentages, `LessonQuestions` for rendering a scored section, `LessonAssign` + `useAssignments()` for giving a lesson to classes.
- Two-click confirmation for destructive buttons (delete, submit, redo), as on the existing pages.
- **i18n** (`@nuxtjs/i18n`, `no_prefix`, default `vi`, choice kept in the `lang` cookie, switch = `LangSwitch` in the sidebar, login and account pages). Every UI string is a key in `i18n/locales/vi.json` + `en.json` (same keys in both): `$t()` in templates, `const { t } = useI18n()` in `<script setup>`, `tr()` from `app/utils/i18n.ts` in plain utils. Label maps that must follow the language are built with `labels(prefix, keys)` (getters). Seeded course/phase names go through `localName()`; lesson content stays as authored. Database and edge-function errors are raised in Vietnamese; show them through `errorText()` (`app/utils/serverErrors.ts`), and add an English pattern there when you add a new `raise exception`. Messages may hold `<b>` (rendered with `v-html`); `@` and `|` are special in vue-i18n (write `{'@'}`, `{'|'}`), and `|` separates plural forms used as `$t(key, n)`.
- Pin new npm dependencies to an exact version published at least two weeks earlier.

Data-access rules for `app/**` live in `.claude/rules/web-data-access.md`; they load automatically when you edit those files.
