# web — Nuxt 4 SPA + Supabase

Run every npm command under Node 24 (`.nvmrc`); the machine default is Node 20, which Nuxt rejects:

```bash
source ~/.nvm/nvm.sh && nvm use && npm run typecheck && npm run build
```

A change is done when `npm run typecheck` and `npm run build` both pass. Logged-in flows can be driven in a headless browser with the test accounts `test.admin` / `test.gv` / `test.hs` (`test.hs` is in class 6T2; `test.gv` teaches no class until an admin assigns one, e.g. a throw-away class made for the check), whose passwords are in the gitignored `.env.test`; say plainly which flows were not tried in a browser.

## Architecture

- **SPA** (`ssr: false`), Vercel Root Directory `web`, env `SUPABASE_URL` / `SUPABASE_KEY`. There are no server routes; all data goes browser → Supabase.
- **Authority is the database.** RLS policies and triggers decide who reads and writes what; the UI only mirrors them. Every permission change is a migration (`db-migration` skill), never a client-side check alone.
- **Roles**: `student`, `teacher`, `admin` (`profiles.role`). Pages declare `definePageMeta({ roles: [...] })`, enforced by `app/middleware/access.global.ts`; admins pass everywhere. Students join a class once by code (`join_class` RPC); teachers see only classes in `class_teachers`. Lessons belong to a grade; a class sees a lesson (row, content, everything) only once it is assigned to that class by a row in `class_lessons`. Working on it (start, save, submit) needs `private.can_work_lesson`: the lesson is not `closed` nor past `due_at` (a pg_cron job, `close-due-lessons`, closes past-due lessons every minute and submits work in progress), and it is `for_all` or the student is in `class_lesson_students`; reading content also lets in a student who already has an attempt (review). `close_class_lesson()` closes and auto-submits; deleting an assignment is refused once the class has attempts. `accessOf()` in `app/utils/course.ts` mirrors this for the UI. On the class page (`/teacher/classes/<id>`) a lesson that is not given yet opens `ClassLessonSetup` (what it contains, which classes of the grade already have it, deadline, whole class or chosen students, results at submit, shuffle); nothing is saved until its "Giao cho lớp" button inserts the `class_lessons` row with those settings (`GiveSettings` in `app/utils/classLesson.ts`) and the `class_lesson_students` rows.
- **Hidden answers**: students never read `section_items`. Lesson questions come from the `lesson_items()` RPC, which strips the answer key until results are released. Students save only their choices in `attempts.answers`; `submit_attempt()` grades on the server, exactly once; graded answers live in `attempt_results`. `class_lessons.show_results` releases results at submit, otherwise on teacher grading. Teachers and admins open lessons in preview (key shown, nothing saved).
- **Accounts**: students (and teachers given one) log in with a username + password issued at `/teacher/students` and `/admin/teachers` (`AccountManager`). A username is the auth email `<username>@users.english4u.internal` (`loginEmail()` in `app/utils/accounts.ts`); Google login remains for admins/teachers. Creating, renaming, resetting passwords, locking (ban + `profiles.active`) and deleting accounts need the service role, so they go through the edge function `supabase/functions/manage-accounts` (deployed with the Supabase MCP `deploy_edge_function`, `verify_jwt: false` because it authenticates the caller itself). The function is the authority there: admins manage anyone but themselves; teachers only students of their classes. Keep its domain constant in sync with `LOGIN_DOMAIN`. Edge functions are Deno code (`npm:` imports): the Nuxt typecheck skips them, and editors check them through the Deno extension (`.vscode/settings.json` → `deno.enablePaths`).
- **Content model**: `courses → phases → lessons → lesson_sections → section_items`, mapped to UI types by `toLesson()` in `app/utils/course.ts`. Question ids are `score_key + item number` (e.g. `M3`); items carry their original number `n`, and every qid is built with `qidOf()` — never from the display index, because `shuffleLesson()` (per-student order when `class_lessons.shuffle`) reorders items and options.
- **Section types**: `explain`, `cards`, `writing` (unscored) and `mcq`, `typed`, `order`, `match`, `error` (scored, graded in `private.grade_attempt()` and mirrored by `gradeLocal()`). `match` pairs `prompt`/`back`; `lesson_items()` hides `back` until release and returns every right side of the section, shuffled, in `options`. `error` stores a sentence's chunks in `options` with the wrong one in `correct_option`; `shuffleLesson()` never reorders its chunks. `mcq`/`typed` may carry a shared reading passage in `lesson_sections.body`. `[x]` in an option or chunk is shown underlined by `markUnderline()` and compared raw when grading. Exam-format starters for the editor are `SECTION_PRESETS` in `app/utils/lessonDraft.ts`. A new section type touches all of these plus `toSection`, `draftPayload`/`draftToLesson`, `validateDraft`, `LessonQuestions`, `LessonWorksheet` and `validate_section_item`.
- **Lesson editor** (`/teacher/lessons/new`, `/teacher/lessons/<id>`): teachers build lessons in a grade they teach from a structure template, saved whole by the `save_lesson()` RPC with an id from `next_lesson_id()`, then assign them to classes. Only the author (`lessons.created_by`) or an admin edits a lesson. A new lesson goes through two stages on one page: setup (grade, term, then the structure step, `lesson-editor/Structure.vue`) and content; an existing lesson opens at its content. The structure step starts from the standard layout, the exam layout (`EXAM_STRUCTURE`), blank, a structure the teacher saved (`lesson_structures`: `structureOf()` stores only section type, title, time, hint, `short`, question count and the exam-preset key, never questions; `sectionsFromStructure()` rebuilds it) or another lesson. Starter questions of a preset (`SECTION_PRESETS`) are built inside `make()`, because `tr()` needs the running app. Draft logic lives in `app/utils/lessonDraft.ts`. Deleting a lesson (lesson list `/courses/<id>` and the editor) goes through `useLessonDelete()`: only the author or an admin (RLS), sections, questions and class assignments cascade, and the database refuses once any student has an attempt (`attempts.lesson_id` is `ON DELETE RESTRICT`), which `lessonDeleteError()` turns into a Vietnamese message; the delete asks for the deleted row back because RLS silently deletes nothing otherwise. Lessons with attempts are read-only. Teachers never type HTML: formatted fields use `RichEditor` (Tiptap; custom `Keyword` = `em.g` and `Callout` = `div.box`/`div.warn` in `app/utils/editorExtensions.ts`), and fields compared when grading (options, answers, order chunks) stay plain inputs. Lesson HTML is rendered through DOMPurify (`safeHtml`); grading compares raw option/answer text, so sanitise only for display.

## Conventions

- `app/types/database.types.ts` is hand-maintained (with `Tables` / `Views` / `Enums` helpers). Add every new table, view, column and RPC there in the same change.
- Hold fetched DB rows in `shallowRef`; a deep `ref` over the recursive `Json` type triggers TS2589.
- The signed-in user id is `useSupabaseUser().value?.sub` (the value holds JWT claims, not a User).
- PostgREST returns embedded rows unordered: sort by `position` on the client.
- Shared UI pieces: `BackLink` for back navigation, `Pager` + `pageRange()` for paging (server lists also drop a stale response when filters change quickly: keep a latest-request counter), `usePaged()` for paging a list already loaded whole, `LessonFilters` + `useLessonFilter()` for lesson lists (search without accents via `fold()`, kind from the label via `lessonKind()`, term, author, a page-specific status), `StatBar` for meters, `accuracyOf(ok, done)` for percentages, `LessonQuestions` for rendering a scored section, `LessonAssign` + `useAssignments()` for giving a lesson to classes.
- Two-click confirmation for destructive buttons (delete, submit, redo), as on the existing pages.
- **i18n** (`@nuxtjs/i18n`, `no_prefix`, default `vi`, choice kept in the `lang` cookie, switch = `LangSwitch` in the sidebar, login and account pages). Every UI string is a key in `i18n/locales/vi.json` + `en.json` (same keys in both): `$t()` in templates, `const { t } = useI18n()` in `<script setup>`, `tr()` from `app/utils/i18n.ts` in plain utils. Label maps that must follow the language are built with `labels(prefix, keys)` (getters). Seeded course/phase names go through `localName()`; lesson content stays as authored. Database and edge-function errors are raised in Vietnamese; show them through `errorText()` (`app/utils/serverErrors.ts`), and add an English pattern there when you add a new `raise exception`. Messages may hold `<b>` (rendered with `v-html`); `@` and `|` are special in vue-i18n (write `{'@'}`, `{'|'}`), and `|` separates plural forms used as `$t(key, n)`.
- Pin new npm dependencies to an exact version published at least two weeks earlier.

Data-access rules for `app/**` live in `.claude/rules/web-data-access.md`; they load automatically when you edit those files.
